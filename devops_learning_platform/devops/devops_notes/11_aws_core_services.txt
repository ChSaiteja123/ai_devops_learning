AWS Core Services
========================

PURPOSE / OVERVIEW
--------------------------------------------------------------------------------
Amazon Web Services (AWS) is the largest public cloud platform. It provides a broad set of services for compute, storage, networking, security, and monitoring.

1. CORE AWS COMPUTE SERVICES
--------------------------------------------------------------------------------
Core AWS compute services

- EC2: virtual machines
- ECS: container orchestration service
- EKS: Kubernetes service
- Lambda: serverless compute

2. CORE AWS STORAGE SERVICES
--------------------------------------------------------------------------------
Core AWS storage services

- S3: object storage
- EBS: block storage for EC2
- EFS: file storage for Linux workloads

3. CORE NETWORKING SERVICES
--------------------------------------------------------------------------------
Core networking services

- VPC: isolated virtual network
- Subnets: segmentation inside VPC
- Internet Gateway: public internet access
- NAT Gateway: private subnet outbound connectivity
- Route53: DNS service
- ELB / ALB: load balancing

4. CORE DATABASE SERVICES
--------------------------------------------------------------------------------
Core database services

- RDS: managed relational database
- DynamoDB: NoSQL database
- ElastiCache: in-memory caching

5. CORE SECURITY AND IDENTITY SERVICES
--------------------------------------------------------------------------------
[SECURITY] Core security and identity services

- IAM: access control
- KMS: encryption keys
- GuardDuty: threat detection
- WAF: web application firewall

6. CORE MONITORING SERVICES
--------------------------------------------------------------------------------
Core monitoring services

- CloudWatch: metrics, logs, alarms
- CloudTrail: API activity logging

7. EXAMPLE ARCHITECTURE
--------------------------------------------------------------------------------
Example architecture

User -> ALB -> EC2 or EKS -> RDS -> S3

10. AWS ACCOUNT AND SERVICE OPERATIONS
--------------------------------------------------------------------------------
EXAMPLE
----------------------------------------
AWS account and service operations
Use AWS Organizations to separate production, security, logging, and sandbox accounts.
Apply service control policies for forbidden regions, public resources, and unsafe services.
Use IAM Identity Center or federation instead of shared IAM users for human access.
Require MFA and short session duration for privileged roles.
Use resource-based policies and identity policies together only when ownership is clear.
Centralize CloudTrail, Config, and security findings in a protected security account.
Enable S3 block public access and default encryption unless a reviewed exception exists.
Use private subnets for application and database tiers, with controlled service endpoints.
Distribute load balancers, autoscaling groups, and critical data paths across availability zones.
Choose ECS, EKS, Lambda, or EC2 from workload operations rather than popularity.
Use SQS to absorb bursts and isolate slow or unavailable consumers.
Use SNS or EventBridge for fan-out and event routing with explicit retry behavior.
Use instance profiles, task roles, execution roles, and function roles with narrow permissions.
Store application credentials in Secrets Manager or Parameter Store with access auditing.
Use KMS key policies, grants, and rotation settings appropriate to the data classification.
Define backup vaults, retention locks, and cross-account copies for critical data.
Test restoration of EBS, RDS, S3, DynamoDB, and configuration state.
Review Route 53, ALB, WAF, and certificate dependencies during failover planning.
Use CloudWatch dashboards for service health and CloudTrail for administrative evidence.
Set alarms for quotas, certificates, backup failures, billing anomalies, and user-facing errors.
Use AWS Config and policy checks to detect drift from encryption, tagging, and network standards.
Estimate NAT, load balancer, CloudWatch, backup, and cross-region transfer cost before launch.
Use Savings Plans, Reserved Instances, and Spot only after workload behavior is measured.
Remove unused elastic IPs, volumes, snapshots, security groups, and test load balancers.
Record the region, account, resource identifiers, deployment digest, and owner for each service.
Keep a provider incident runbook with status-page checks, traffic controls, and escalation contacts.
AWS operations require account boundaries, identity discipline, tested recovery, and cost visibility.

11. AWS ACCOUNT GOVERNANCE
--------------------------------------------------------------------------------
EXAMPLE
----------------------------------------
AWS account governance
Use an organization structure that separates workloads from security and centralized logging.
Protect the organization management account and avoid running application resources there.
Use service control policies as guardrails, not as a replacement for IAM least privilege.
Create dedicated roles for auditors, developers, operators, and automation.
Use external identity federation for people and short-lived role sessions.
Review role trust policies for wildcard principals and unintended external accounts.
Secure root credentials, require MFA, and reserve root for tasks that require it.
Enable CloudTrail in every account and region required by the governance policy.
Centralize CloudTrail, Config, GuardDuty, and Security Hub findings in protected accounts.
Protect audit buckets with restrictive policies, versioning, encryption, and retention controls.
Use Config rules to detect public storage, missing encryption, unrestricted ports, and missing tags.
Route high-confidence findings to an incident workflow with an owner and response target.

12. AWS SERVICE SELECTION
--------------------------------------------------------------------------------
EXAMPLE
----------------------------------------
AWS service selection
Choose EC2 when host control or specialized software outweighs management overhead.
Choose ECS when container scheduling is needed without operating a Kubernetes control plane.
Choose EKS when Kubernetes APIs, ecosystem, or portability justify the added responsibility.
Choose Lambda for event-driven tasks with bounded execution and compatible startup behavior.
Use SQS for durable buffering and retry isolation between producers and consumers.
Use SNS for fan-out notifications and EventBridge for event filtering and routing.
Use S3 for objects, not for transactional row updates or low-latency mutable records.
Use EBS for instance-attached block storage and EFS for shared filesystem semantics.
Use RDS for relational transactions and DynamoDB for known high-scale access patterns.
Use ElastiCache only when the application defines stale-data and cache-outage behavior.
Review quotas, regional availability, encryption support, and operational ownership before adoption.
Record the reason for selecting a service and the conditions that would trigger reevaluation.

13. AWS RELIABILITY AND SECURITY CHECKS
--------------------------------------------------------------------------------
EXAMPLE
----------------------------------------
AWS reliability and security checks
Distribute critical compute and load balancing across availability zones.
Use private subnets and VPC endpoints for internal workloads and AWS API access where appropriate.
Use load balancer health checks that represent application readiness.
Use autoscaling with capacity limits that protect downstream databases and service quotas.
Use immutable AMIs, container digests, or function versions for repeatable deployment.
Keep backup copies in a separate account or recovery boundary when deletion is a concern.
Test restore of data and infrastructure with the same identities and network assumptions used in production.
Monitor certificate expiry, quota consumption, backup health, queue age, and user-facing latency.
Use CloudWatch alarms and dashboards with owners, runbooks, and sensible missing-data behavior.
Record deployment IDs and resource identifiers in logs for incident correlation.
Use WAF, Shield, security groups, NACLs, and IAM as complementary controls.
Review public access findings before launch and after every network or policy change.

14. AWS COST CONTROLS
--------------------------------------------------------------------------------
EXAMPLE
----------------------------------------
AWS cost controls
Use cost allocation tags and account boundaries to make ownership visible.
Set budgets for NAT, load balancers, CloudWatch logs, backups, data transfer, and storage.
Use S3 lifecycle rules and log retention that match investigation and compliance needs.
Delete idle resources, stale snapshots, old AMIs, unused elastic IPs, and test load balancers.
Compare Savings Plans, Reserved Instances, Spot, and on-demand pricing against actual usage.
Estimate cross-zone, cross-region, NAT processing, and managed-service charges before scaling.
AWS operations are strongest when security, reliability, and cost decisions share the same ownership model.
Use resource policies and identity policies only after determining which account owns the resource.
Keep service-linked roles under review and document why each trusted AWS service needs access.
Use regional and zonal failure tests for critical paths instead of assuming provider availability.
Keep deployment artifacts immutable and record the digest in CloudWatch and change records.
Use queue dead-letter handling and replay controls for event-driven services.
Monitor account quotas, API throttling, and failed automation separately from application errors.
Use private connectivity for control-plane calls when the threat model and service support it.
Review cross-account trust whenever teams, vendors, or organizational units change.
Document the minimum permissions needed to restore each backup and infrastructure component.
AWS service ownership includes lifecycle, access review, recovery proof, and retirement cleanup.
Review service limits before every major launch and record approved quota increases.
Keep provider escalation contacts and account identifiers in the operational runbook.
