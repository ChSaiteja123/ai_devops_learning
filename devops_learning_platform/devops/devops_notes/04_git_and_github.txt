Git and GitHub
========================

PURPOSE / OVERVIEW
--------------------------------------------------------------------------------
Git is a distributed version control system used to track code changes. GitHub is a web-based hosting service for Git repositories.

1. GIT CONCEPTS
--------------------------------------------------------------------------------
Git concepts

- repository
- commit
- branch
- merge
- pull request
- clone
- fetch
- pull
- push

2. COMMON COMMANDS
--------------------------------------------------------------------------------
Common commands

- git init
- git clone <url>
- git status
- git add .
- git commit -m "message"
- git push origin main
- git pull origin main
- git branch
- git checkout -b feature/login
- git merge feature/login

3. EXAMPLE
--------------------------------------------------------------------------------
Example

EXAMPLE
----------------------------------------
git init
git add .
git commit -m "Initial project setup"
git branch -M main
git remote add origin <repo-url>
git push -u origin main

4. BRANCHING STRATEGY
--------------------------------------------------------------------------------
Branching strategy

- main: production-ready code
- develop: integration branch
- feature/*: feature work
- hotfix/*: urgent production fixes

5. PULL REQUEST WORKFLOW
--------------------------------------------------------------------------------
Pull request workflow

1. create feature branch
2. commit changes
3. push branch
4. open pull request
5. review and approve
6. merge to main

6. GITHUB BEST PRACTICES
--------------------------------------------------------------------------------
GitHub best practices
[SECURITY] Never commit credentials or other secrets; rotate them immediately if they enter repository history.

- use meaningful commit messages
- protect main branch
- use PR reviews
- enable CI checks
- use tags for releases

9. REPOSITORY RECOVERY AND RELEASE PRACTICE
--------------------------------------------------------------------------------
Repository recovery and release practice
Record the remote URL, default branch, and required Git version in repository documentation.
Use git remote -v and git ls-remote to verify that a recovery target is reachable.
Create a mirror backup when all branches, tags, and notes must be preserved.
Test recovery by cloning the backup into a clean directory.
Protect release tags from force pushes and accidental deletion.
Use a changelog that links user-visible behavior to commit or pull request identifiers.
Create a release candidate from a reviewed commit, not from an uncommitted workspace.
Verify the built artifact checksum before publishing release metadata.
Use git diff --stat and git diff --check as inexpensive review gates.
Use git clean only after previewing untracked files with a dry run.
Recover lost local work with reflog before attempting manual object manipulation.
Treat repository permissions as production permissions when workflows can deploy.
Review branch protection after changes to teams, applications, or ownership.
Document how to disable a compromised workflow token and rotate related secrets.
