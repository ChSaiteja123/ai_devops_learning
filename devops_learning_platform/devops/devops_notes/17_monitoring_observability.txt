Monitoring and Observability
============================

PURPOSE / OVERVIEW
--------------------------------------------------------------------------------
Monitoring is the continuous collection and analysis of system and application data. Observability is the ability to understand system health based on metrics, logs, and traces.

1. THREE PILLARS OF OBSERVABILITY
--------------------------------------------------------------------------------
Three pillars of observability

- metrics: numerical values such as CPU, memory, request rate
- logs: event records from applications and systems
- traces: track a request across multiple services

2. COMMON TOOLS
--------------------------------------------------------------------------------
Common tools

- Prometheus
- Grafana
- Alertmanager
- CloudWatch
- ELK stack
- Datadog
- OpenTelemetry

3. EXAMPLE METRICS
--------------------------------------------------------------------------------
Example metrics

- CPU usage
- memory usage
- HTTP 500 count
- request latency
- pod restarts

4. PROMETHEUS EXAMPLE
--------------------------------------------------------------------------------
Prometheus example

5. WHY MONITORING MATTERS
--------------------------------------------------------------------------------
Why monitoring matters

- detect failure early
- identify bottlenecks
- reduce downtime
- improve incident response

6. PRODUCTION GUIDANCE
--------------------------------------------------------------------------------
Alertmanager receives Prometheus alerts and routes them to notification systems such as email, Slack, PagerDuty, or webhooks. It groups duplicate alerts and supports inhibition rules so one infrastructure failure does not create hundreds of redundant messages.
[IMPORTANT] Every production alert needs a clear owner, actionable response, and tested notification route.

7. EXAMPLE ALERT RULE
--------------------------------------------------------------------------------
Example alert rule

EXAMPLE
----------------------------------------
groups:
  - name: service-health
    rules:
      - alert: ServiceDown
        expr: up == 0
        for: 2m
        labels:
          severity: critical

8. CORE CONCEPTS
--------------------------------------------------------------------------------
Observability turns infrastructure into a system you can reason about and troubleshoot reliably.

Observability deep dive

Observability helps explain unknown failure modes.
Metrics are efficient for trends and alert thresholds.
Logs preserve detailed events and diagnostic context.
Traces connect a request across service boundaries.
Use consistent service, environment, version, and region labels.
Avoid unbounded metric label cardinality.
Use rate, errors, duration, and saturation signals.
Define service level indicators from user experience.
Set service level objectives with an error budget.
Alert when the budget is consumed too quickly.
Page on symptoms that require immediate human action.
Ticket lower urgency risks for planned work.
Every alert needs an owner and runbook.
Include dashboard and trace links in notifications.
Use recording rules for expensive Prometheus queries.
Keep scrape intervals appropriate to signal urgency.
Use exporters for hosts and managed services.
Protect Prometheus and Grafana with authentication.
Restrict metric endpoints from public access.
Use Alertmanager grouping and inhibition to reduce storms.
Test notification receivers and routing changes.
Use structured JSON logs with correlation identifiers.
Centralize logs with retention and access controls.
Redact tokens, passwords, and private data before shipping.
Use log sampling only after preserving incident evidence.
Set retention by operational and compliance requirements.
Use trace sampling that preserves errors and slow requests.
Propagate trace context across queues and HTTP calls.
Instrument database, cache, and external calls.
Add deployment markers to all service dashboards.
Correlate changes with latency and error shifts.
Use exemplars to connect metrics with traces.
Measure queue depth, age, and consumer lag.
Monitor retries because they can hide dependency failure.
Track circuit breaker state and timeout rates.
Monitor certificate, quota, disk, and backup expiry.
Use synthetic tests for critical user journeys.
Test observability during failure drills.
Verify dashboards remain useful at high cardinality.
Control telemetry storage and ingestion costs.
Sample high-volume debug data during normal operation.
Keep critical audit events unsampled.
Review noisy alerts after every incident.
Delete alerts that never lead to action.
Use maintenance silences with owner and expiry.
Avoid alerting on every pod restart or log line.
Build dashboards around decisions, not vanity metrics.
Separate executive summaries from operator detail.
Use annotations for deployments and incidents.
Define expected baselines for latency and traffic.
Use anomaly detection only with a clear response.
Check time synchronization across telemetry sources.
Use UTC timestamps for cross-system analysis.
Keep collector pipelines redundant for critical services.
Protect telemetry queues from backpressure and data loss.
Monitor exporters and collectors as services themselves.
Use black-box and white-box checks together.
Practice incident triage from a blank dashboard.
Write postmortems using evidence from metrics, logs, and traces.
Observability is valuable when it shortens diagnosis and recovery.

10. OBSERVABILITY IMPLEMENTATION AND INCIDENT PRACTICE
--------------------------------------------------------------------------------
Observability implementation and incident practice
Start with the customer journey and define which signals prove success or failure.
Choose metric names, units, labels, and aggregation rules before adding dashboards.
Keep service, environment, version, region, and instance identity consistent across telemetry.
Use histograms or summaries deliberately for latency and document percentile interpretation.
Avoid user IDs, request IDs, or URLs as unbounded metric labels.
Use structured logs with timestamps, severity, service, version, trace ID, and safe context.
Redact credentials, tokens, payment data, and unnecessary personal information at the source.
Propagate trace context across HTTP, message queues, scheduled work, databases, and caches.
Sample normal traffic while retaining errors, slow requests, and representative exemplars.
Use black-box checks for user availability and white-box metrics for diagnosis.
Create recording rules for expensive or repeated Prometheus queries.
Set scrape intervals from signal urgency and storage budget, not habit.
Protect metrics endpoints, Grafana, Prometheus, collectors, and alert configuration with authentication.
Replicate or buffer telemetry pipelines when losing data would impair incident response.
Monitor collectors, exporters, queues, and storage as production services.
Define an SLI, SLO, error budget, and response owner for each important service.
Page only when a person must act soon; create tickets for risks that can wait.
Include severity, affected service, dashboard, trace query, runbook, and owner in every page.
Set alert duration and missing-data behavior to avoid transient noise and silent failure.
Use grouping, inhibition, and maintenance silences with an owner and expiration.
Test all notification receivers after configuration, credential, or routing changes.
Use deployment and incident annotations to compare change markers with metric shifts.
Monitor queue age, retry rate, circuit breaker state, timeout rate, and dependency saturation.
Alert on certificate expiry, backup failure, quota exhaustion, disk capacity, and telemetry loss.
Build separate overview, service, dependency, and deep-diagnosis dashboards.
Prefer panels that support a decision over panels that merely display available data.
Control retention and ingestion cost with sampling, aggregation, compression, and tiering.
Retain audit and security events according to policy even when debug telemetry is sampled.
Practice incident triage from a blank dashboard and verify that links remain valid.
Use postmortem evidence to remove noisy alerts, add missing signals, and improve runbooks.
Observability is an operational product with owners, budgets, tests, and recovery requirements.

11. TELEMETRY ARCHITECTURE
--------------------------------------------------------------------------------
Telemetry architecture
Define a service telemetry contract covering metric names, log fields, trace context, and retention.
Use OpenTelemetry resource attributes for service, version, environment, region, and deployment identity.
Keep collectors close to workloads when local buffering prevents data loss during network disruption.
Use a gateway or central collector for filtering, routing, sampling, and policy enforcement.
Protect collector endpoints with authentication and limit who can submit or query telemetry.
Use queues or persistent buffers when the backend can become temporarily unavailable.
Monitor collector queue depth, export errors, dropped spans, scrape failures, and backend latency.
Keep a minimal local signal when the central telemetry platform is unavailable.
Separate operational telemetry from security audit records with different access and retention rules.
Test upgrades to collectors, exporters, agents, and dashboard plugins before broad rollout.

12. METRIC DESIGN
--------------------------------------------------------------------------------
Metric design
Use counters for totals, gauges for current values, and histograms for distributions.
Record request rate, error rate, duration, and saturation for each important service.
Use dimensions that support a decision and remove labels that create unbounded series.
Define units and aggregation behavior so dashboards do not compare incompatible values.
Use recording rules for common ratios, rates, and service-level indicators.
Check for counter resets and missing scrapes before interpreting a sudden trend.
Use exemplars to connect a metric observation to a trace without adding trace IDs as labels.
Measure queue age and consumer lag, not only queue depth.
Measure retry and timeout rates because successful retries can hide dependency failure.
Publish business metrics such as checkout success, job completion, or message processing delay.
Review metric cardinality and storage growth after adding a new label or instrumentation library.

13. LOGS AND TRACES
--------------------------------------------------------------------------------
Logs and traces
Emit one structured event per meaningful state change rather than unbounded debug text.
Include a correlation ID, trace ID, request outcome, duration, dependency, and safe error category.
Redact secrets at the application boundary before logs leave the workload.
Use consistent severity levels and avoid treating expected client errors as operator pages.
Retain error and audit evidence longer than routine informational logs when policy requires it.
Use trace spans for network, database, cache, queue, and external provider calls.
Propagate context through asynchronous messages and preserve parent identifiers during retries.
Sample normal traces while retaining errors, slow traces, and representative traffic.
Check clock synchronization before comparing event order across hosts and regions.
Use logs for exact events, metrics for aggregate behavior, and traces for path analysis.

14. ALERT AND DASHBOARD PRACTICE
--------------------------------------------------------------------------------
Alert and dashboard practice
Tie every page to a service objective, an owner, and a documented response action.
Use a pending duration to avoid paging on short-lived noise.
Set thresholds from baselines and capacity limits rather than arbitrary round numbers.
Define no-data behavior so a broken exporter cannot silently appear healthy.
Use inhibition when a parent dependency failure explains many child alerts.
Expire maintenance silences and review them after each incident.
Test receiver credentials, escalation policies, and webhook payloads regularly.
Build dashboards for overview, service health, dependencies, deployments, and diagnosis.
Include deployment, rollback, incident, and maintenance annotations on time-series panels.
Practice finding the first bad signal from a clean dashboard during game days.

15. COST, PRIVACY, AND GOVERNANCE
--------------------------------------------------------------------------------
Cost, privacy, and governance
Set retention by operational need, compliance, and recovery evidence.
Control ingestion with sampling, aggregation, compression, and debug-level limits.
Avoid high-cardinality labels and verbose payloads that reveal private data or inflate cost.
Restrict access to logs and traces containing customer, security, or infrastructure details.
Audit dashboard, alert, collector, and retention policy changes.
Review telemetry cost alongside service growth and remove signals that never support a decision.
Observability improves reliability only when signals are trustworthy, actionable, affordable, and tested.
Telemetry recovery checklist
Keep dashboard and alert definitions in version control with review and ownership metadata.
Back up critical alert routes, recording rules, dashboards, and collector configuration.
Test restoring monitoring configuration into an isolated environment before a platform migration.
Verify that alerts still reach the on-call system after identity, certificate, or endpoint changes.
Keep a minimal synthetic check independent of the primary telemetry stack.
Use deployment markers and incident annotations to preserve causal evidence during retention cleanup.
Review sampling and redaction rules after adding new services or data fields.
Observability recovery is part of service recovery because blind operation increases outage duration.
Record telemetry restoration time and the signals unavailable during the gap.
Review alert ownership and runbook links after service ownership changes.
Keep a tested fallback contact path when the primary paging platform is unavailable.

16. OBSERVABILITY AUTOMATION
--------------------------------------------------------------------------------
Observability automation converts telemetry events into consistent, auditable
operational decisions. It should reduce manual repetition without hiding the
evidence an engineer needs during an incident.

[IMPORTANT] Treat every incoming alert as untrusted input. Validate its shape,
labels, status, fingerprint, and permitted values before routing it.

17. ALERT EVENT CONTRACT
--------------------------------------------------------------------------------
Define a minimum alert contract before building automation.
Required fields commonly include alert name, service, severity, environment,
status, summary, owner, and a stable fingerprint.
Reject events that have missing identity or severity information.
Reject unknown severity values instead of silently routing them.
Keep label names consistent across services so grouping remains predictable.
Do not place secrets, tokens, or customer data in alert labels.
Keep runbook URLs in annotations and validate allowed URL schemes.
Distinguish firing, resolved, pending, and unknown states.
Record the source receiver and ingestion timestamp.

18. FINGERPRINT DEDUPLICATION
--------------------------------------------------------------------------------
Alertmanager may deliver the same logical event more than once.
Use a stable fingerprint to identify a logical alert instance.
Keep a short-lived idempotency store for recently processed fingerprints.
Record duplicate count as a metric and in the audit record.
Do not deduplicate different incidents merely because their text is similar.
Include service, environment, alert name, and relevant identity in the key.
Define how fingerprints behave when an alert resolves and later fires again.
Expire old keys so a future legitimate incident is not suppressed forever.

19. SEVERITY ROUTING
--------------------------------------------------------------------------------
Route events according to impact and urgency.
Critical events may page an on-call engineer.
Warning events may create a ticket or team notification.
Informational events may enter a digest or dashboard.
Every route needs an owner, escalation target, and runbook.
Keep routing policy in version control and review changes.
Test routes with synthetic events before changing production receivers.
Use grouping to combine related events and inhibition to suppress dependent noise.
Set repeat intervals that match the expected response time.
Never treat routing as authorization to modify infrastructure.

20. AUDITABLE NOTIFICATION PLANS
--------------------------------------------------------------------------------
Create an intermediate notification plan before sending messages.
The plan should contain generation time, source status, unique count, duplicate
count, group severity, receiver, services, alert names, and runbooks.
Record whether a notification was actually sent.
Record failures separately from successful delivery.
Keep the plan free of secrets and unnecessary personal data.
Retain plans long enough to support incident review and compliance needs.
Use immutable or access-controlled storage for important audit records.
Connect the plan to deployment IDs and incident IDs when available.

21. WEBHOOK AND RECEIVER SAFETY
--------------------------------------------------------------------------------
Authenticate webhook requests and restrict network access to receivers.
Apply request size limits and timeouts.
Validate content type and JSON structure.
Use bounded retries with exponential backoff for transient delivery failures.
Send failed events to a durable retry or dead-letter path.
Do not retry invalid payloads or rejected authorization.
Redact secrets before sending to chat, email, or ticket systems.
Protect receiver credentials with a secret manager.
Test receiver failure without creating a notification storm.
Monitor queue age, delivery latency, retry count, and permanent failures.

22. SAFE REMEDIATION BOUNDARY
--------------------------------------------------------------------------------
Alert automation may recommend an action, but recommendation and execution are
different trust boundaries.
Keep kubectl, cloud, database, and rollback credentials outside the parser.
Require explicit authorization before high-impact remediation.
Use an allowlist of approved action types.
Validate target service, namespace, environment, and image before execution.
Use dry-run mode as the default for new automation.
Require human approval for production rollback, scaling, or traffic changes.
Log operator identity, reason, command, result, and approval evidence.
Make remediation idempotent and reversible.

23. CI VALIDATION FOR OBSERVABILITY AUTOMATION
--------------------------------------------------------------------------------
Compile the router and run unit tests on every change.
Test missing labels, invalid severity, missing fingerprints, and malformed JSON.
Test duplicate fingerprints and resolved alert events.
Test critical, warning, and informational routing.
Test empty alert groups and unknown receiver behavior.
Archive generated plans as build evidence.
Keep test payloads free of real credentials and customer data.
Run security scans on dependencies and container images.
Use a protected deployment stage for production receivers.
Pause notification changes during active incidents unless the change is urgent.
