1. Core Concepts

Concept Q1. What is the difference between a Docker image and a Docker container?
An image is an immutable, layered filesystem snapshot with metadata. A container is a live, isolated process created from an image — it adds a thin writable layer on top. Multiple containers can run from the same image without affecting it.
Concept Q2. What is a Docker registry and name two examples?
A registry stores and distributes Docker images. Examples: Docker Hub (public default registry) and Amazon ECR (AWS-managed private registry). Others include GitHub Container Registry and Google Artifact Registry.
Concept Q3. Why should production use image digests instead of tags like latest?
Tags are mutable — a tag like latest can be overwritten to point to a different image at any time. A digest (sha256:abc123...) is immutable and always refers to the same exact content, ensuring reproducibility and rollback safety.
Concept Q4. What does a multi-stage Dockerfile achieve?
Multi-stage builds use multiple FROM instructions. Early stages compile/build the application. Only necessary artifacts are copied into the final minimal stage. This removes compilers, build tools, and dev dependencies from the runtime image — reducing size and attack surface.
Concept Q5. What is .dockerignore and why is it important?
.dockerignore tells the Docker build daemon which files to exclude from the build context. It prevents sensitive files (e.g., .env, .git, private keys) from being accidentally copied into the image and speeds up builds by reducing context size.

2. Dockerfile

Dockerfile Q6. Write a multi-stage Dockerfile for a Python Flask app that runs as a non-root user.
# Stage 1: build/deps FROM python:3.11-slim AS builder WORKDIR /app COPY requirements.txt . RUN pip install --no-cache-dir --user -r requirements.txt # Stage 2: runtime FROM python:3.11-slim WORKDIR /app COPY --from=builder /root/.local /home/appuser/.local COPY . . RUN useradd -m appuser USER appuser ENV PATH=/home/appuser/.local/bin:$PATH EXPOSE 5000 CMD ["python", "app.py"]
Dockerfile Q7. What is the difference between CMD and ENTRYPOINT?
ENTRYPOINT defines the main executable — it cannot be overridden by arguments at docker run. CMD provides default arguments to ENTRYPOINT or a default command if no entrypoint is set. Use exec-form (JSON array) for both to ensure correct signal delivery (SIGTERM propagation).

ENTRYPOINT ["python", "app.py"] CMD ["--port", "5000"] # overridable default args
Dockerfile Q8. Why copy requirements.txt before the rest of the source code?
Docker caches each layer. If requirements.txt hasn't changed, Docker reuses the cached layer with all installed packages — skipping the slow pip install. Copying source code last means only code changes invalidate the source layer, not the dependency layer.
Security Q9. How do you pass secrets during a Docker build without baking them into an image layer?
Use BuildKit secret mounts. The secret is never written to a layer.
# Dockerfile RUN --mount=type=secret,id=mytoken \ pip install --extra-index-url $(cat /run/secrets/mytoken) privatepackage # Build command DOCKER_BUILDKIT=1 docker build --secret id=mytoken,src=./token.txt .
Dockerfile Q10. What does HEALTHCHECK do in a Dockerfile? Write an example.
HEALTHCHECK tells Docker how to test that the container is still working. Docker marks it healthy/unhealthy based on the exit code.
HEALTHCHECK --interval=30s --timeout=5s --start-period=15s --retries=3 \ CMD curl -f http://localhost:5000/health || exit 1
Set --start-period to give slow-starting apps (migrations, warm-up) time before health checks begin.

Reverse it to copy from host into container: docker cp ./config.yml web:/app/config.yml

Add --no-stream for a single snapshot instead of live streaming.

4. Networking

Concept Q18. What is a user-defined bridge network and why use it over the default bridge?
A user-defined bridge network provides automatic DNS-based service discovery — containers can reach each other by container name. The default bridge requires manual IP management or --link (deprecated). User-defined networks also provide better isolation.
docker network create mynet docker run -d --network mynet --name db postgres:15 docker run -d --network mynet --name app myapp:v1.2 # 'app' can reach 'db' via hostname 'db'
Concept Q19. What is the difference between host, bridge, and none network modes?
bridge: default isolated network with port mapping. Containers get their own network namespace.
host: container shares the host's network stack — no port mapping needed, but no isolation.
none: container has no network interface at all — useful for batch jobs that need full isolation.
Command Q20. Inspect which networks a container named web is connected to.
docker inspect web --format '{{json .NetworkSettings.Networks}}' | python -m json.tool

5. Volumes & Storage

Concept Q21. What is the difference between a Docker volume and a bind mount?
Volume: managed by Docker, stored in /var/lib/docker/volumes/. Portable, backed up easily, not tied to host path structure.
Bind mount: maps a specific host path into the container. Useful for development (live code changes) but host-path dependent — not recommended for production data.
Command Q22. Run a PostgreSQL container with a named volume for data persistence.
docker volume create pgdata docker run -d \ --name postgres \ -e POSTGRES_PASSWORD=secret \ -v pgdata:/var/lib/postgresql/data \ postgres:15
Concept Q23. What is a tmpfs mount and when would you use it?
A tmpfs mount stores data in the host's memory only — never written to disk. Use it for sensitive short-lived files (tokens, session keys) that must not persist after the container stops.
docker run --tmpfs /run/secrets:rw,size=10m myapp:v1.2

7. Security

Security Q27. List 5 Dockerfile / runtime security best practices.
1. Run as a non-root user (USER appuser)
2. Use a read-only root filesystem (--read-only flag or readOnlyRootFilesystem: true in K8s)
3. Drop Linux capabilities (--cap-drop=ALL --cap-add=NET_BIND_SERVICE only what's needed)
4. Never bake secrets into image layers — use BuildKit secrets or runtime secret mounts
5. Scan images with Trivy before pushing: trivy image --severity HIGH,CRITICAL myapp:v1.2
Security Q28. How do you scan a Docker image for vulnerabilities using Trivy?
# Scan and fail CI on HIGH or CRITICAL findings trivy image --severity HIGH,CRITICAL --exit-code 1 myapp:v1.2 # Generate SBOM (Software Bill of Materials) trivy image --format cyclonedx --output sbom.json myapp:v1.2
Security Q29. Why is mounting the Docker socket (/var/run/docker.sock) into a container dangerous?
Mounting the Docker socket gives the container full control over the Docker daemon — it can create privileged containers, mount any host path, or escape isolation entirely. This is effectively root access to the host. Never mount it into untrusted workloads. Use scoped APIs or Kaniko/Buildah for CI image builds instead.

8. Production Operations

Production Q30. A container keeps restarting. What is your diagnostic approach?
1. docker ps -a — check exit code and restart count
2. docker logs --tail 100 <container> — look for startup errors
3. docker inspect <container> — check environment, mounts, health state
4. Check for OOMKilled: exit code 137 means memory limit exceeded → increase memory limit or fix leak
5. Check for missing env vars, failed DB connection, or missing config files
6. Run the image manually: docker run --rm -it myapp:v1.2 /bin/sh to explore interactively
Production Q31. How do you implement a graceful shutdown in a Docker container?
1. Use exec-form ENTRYPOINT so PID 1 is your app, not a shell (shell-form wraps in /bin/sh -c which may not forward SIGTERM)
2. Handle SIGTERM in your app code to finish in-flight requests
3. Set --stop-timeout to give enough time: docker stop --time=30 web
4. In Compose: stop_grace_period: 30s
ENTRYPOINT ["python", "app.py"] # exec-form, not shell-form
Production Q32. How do you push an image to Amazon ECR?
# 1. Authenticate aws ecr get-login-password --region us-east-1 \ | docker login --username AWS --password-stdin \ 123456789.dkr.ecr.us-east-1.amazonaws.com # 2. Tag docker tag myapp:v1.2 \ 123456789.dkr.ecr.us-east-1.amazonaws.com/myapp:v1.2 # 3. Push docker push 123456789.dkr.ecr.us-east-1.amazonaws.com/myapp:v1.2
Production Q33. What does docker system df show and why is it useful?
docker system df shows disk usage broken down by images, containers, volumes, and build cache — with sizes and reclaimable space. Use it before pruning to understand what will be removed and to identify disk pressure root cause.

9. Advanced Topics

Concept Q34. What is an SBOM and why does it matter for containers?
An SBOM (Software Bill of Materials) is a machine-readable inventory of all packages, libraries, and licenses inside an image. It matters because:
• Enables rapid CVE impact analysis ("which images use log4j 2.14?")
• Required for compliance (US Executive Order 14028)
• Supports license auditing
Generate with: trivy image --format cyclonedx myapp:v1.2 or syft myapp:v1.2
Concept Q35. What is rootless Docker and why use it?
Rootless Docker runs the daemon and containers as an unprivileged user (no root). This means a container escape does not grant root on the host. It reduces the blast radius of daemon-level vulnerabilities. Trade-off: some features (host networking, certain volume mounts) have compatibility limitations.
Concept Q36. Explain Docker layer caching and how to optimize it for a Node.js app.
Each Dockerfile instruction creates a cache entry. If inputs haven't changed, Docker reuses it. For Node.js:
FROM node:20-slim WORKDIR /app # Copy package files FIRST — cached unless deps change COPY package.json package-lock.json ./ RUN npm ci --omit=dev # Copy source AFTER — only this layer rebuilds on code changes COPY . . CMD ["node", "server.js"]
Production Q37. How do you set CPU and memory limits on a container?
# CLI docker run -d --cpus="0.5" --memory="256m" myapp:v1.2 # Compose services: web: image: myapp:v1.2 deploy: resources: limits: cpus: '0.5' memory: 256M reservations: memory: 128M
Security Q38. What is --cap-drop=ALL and when would you add specific capabilities back?
--cap-drop=ALL removes all Linux capabilities from the container. You add back only what the app needs:
docker run --cap-drop=ALL --cap-add=NET_BIND_SERVICE myapp:v1.2 # NET_BIND_SERVICE: needed to bind ports below 1024 # CHOWN: needed to change file ownership # SYS_PTRACE: needed for debuggers (avoid in prod)
This follows least-privilege: an app binding port 443 only needs NET_BIND_SERVICE, not all root capabilities.
Production Q39. How do you configure Docker to send container logs to a centralized system like CloudWatch?
# Using awslogs driver docker run -d \ --log-driver=awslogs \ --log-opt awslogs-region=us-east-1 \ --log-opt awslogs-group=/myapp/production \ --log-opt awslogs-stream=web-01 \ myapp:v1.2 # Or configure as daemon default in /etc/docker/daemon.json { "log-driver": "awslogs", "log-opts": { "awslogs-region": "us-east-1", "awslogs-group": "/docker/production" } }
Production Q40. Describe the full Docker image release pipeline from code commit to production deployment.
1. Commit triggers CI (GitHub Actions / Jenkins)
2. Build: docker build with BuildKit, multi-stage, no secrets in layers
3. Lint: hadolint Dockerfile for best practice violations
4. Scan: trivy image --exit-code 1 --severity HIGH,CRITICAL
5. Generate SBOM: syft or trivy sbom
6. Sign: cosign sign with keyless signing via OIDC
7. Push to registry: tag with commit SHA, push to ECR/GCR
8. Promote digest: the same digest moves through staging → production (never rebuild)
9. Deploy: Kubernetes rolling update using the pinned digest
10. Verify: smoke tests, health checks, rollback digest retained
